## Codebase Patterns
- Use Pest for all tests, not PHPUnit
- Filament resources live in app/Filament/Resources/{ResourceName}/
- Filament resource pages, schemas, tables, widgets are in subdirectories of the resource
- Always run vendor/bin/pint --dirty before committing
- PersonaStatsWidget uses instance property `protected ?string $pollingInterval = null` (NOT static)
- PersonaStorageService handles file I/O for personas at storage_path("personas/{slug}")
- PersonaObserver auto-initializes storage on create, syncs prompt.md on master_prompt update
- Factories are in database/factories/ and follow the convention of states for different scenarios
- Filament tests authenticate user and set panel: `Filament::setCurrentPanel(Filament::getPanel('admin'))`
- Claude execution via proc_open: use `env -i` with explicit env vars, `/usr/bin/claude -p`, `--output-format stream-json`
- PersonaCycleService handles orchestration; RunPersonaSubtaskJob handles individual subtask execution
- TelegramService mock pattern: `Mockery::mock(TelegramService::class)` + `app()->instance()`
- Telegram callback_data format: `action:id` (e.g. `approve_subtasks:123`); parsed via explode(':')
- Double approval gate: ProposalExecutionService forks persona proposals to GeneratePersonaSubtasksJob, then subtask approval triggers PersonaCycleService::startSubtaskExecution()
- Telegram webhook test pattern: postJson with X-Telegram-Bot-Api-Secret-Token header, mock TelegramService, set config values
- RunPersonaCycleJob handles full analysis cycle: workspace creation, repo clone, Claude execution, output parsing, proposal creation, stats update, cleanup
- Persona status lifecycle: Active -> Running -> AwaitingApproval -> Active (or back to Active on failure)
- Schedule integration: persona_id on TaskSchedule determines job type (RunPersonaCycleJob vs RunScheduledTaskJob)
